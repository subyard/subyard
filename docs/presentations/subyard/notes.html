Slide 02 ↗

Container or VM?

Compare containers in general with virtual machines. Containers isolate ordinary processes through namespaces and related OS mechanisms. Programs still run on the host kernel, alongside other host processes, which keeps overhead low. CPU and memory limits can overlap: they are ceilings on use, not necessarily dedicated reservations. Simultaneous demand still has to fit the real machine.

A VM has a guest OS and kernel behind a hypervisor boundary. That generally provides stronger separation, but the guest OS and virtualization add memory, storage, and runtime CPU costs. Reserved RAM and allocated disk capacity can sit unused while a workload is idle. VM platforms are available on proprietary hosts such as Windows and macOS and can run supported proprietary guest systems; exact combinations depend on the hypervisor and architecture.

Allocation is a policy choice, not an absolute container/VM distinction. VMs can also overcommit CPU and memory; dynamic memory and sparse disks can reduce idle capacity costs. CPU overhead varies with the workload and virtualization path. Containers are not universally Linux-only: Windows process-isolated containers also share their host kernel. A container runtime can itself run inside a VM, adding both layers.

Sources: Docker: containers versus VMs; namespaces and isolation; resource constraints; Microsoft: Windows container isolation; Red Hat: VM overcommit; Microsoft: dynamic VM memory; Microsoft: virtualization CPU overhead; Oracle: host and guest OS support.

Slide 03 ↗

Five agents. One shared 32 GB pool.

The requirement is to share physical capacity across container workspaces and allocate heavy resources dynamically. All five agents run on the same host OS. Agent 1 currently leases an Android emulator; Agent 2 leases a larger disposable VM. The other three have no heavy resource allocated. When a lease ends, the resource is disposed and its capacity becomes available to another agent.

The diagram separates limits from current consumption. Container memory limits are ceilings: their sum can exceed physical RAM without reserving that amount for every workspace. This overcommit is useful when agents reach their peaks at different times. A leased VM is a separate heavy resource charged to the same host capacity; the drawing does not imply that its memory is accounted inside the requesting container's memory limit.

The illustrative snapshot uses 1 GB per agent (5 GB total), 6 GB for the emulator, 10 GB for the disposable VM, and 3 GB for the host and other services. That is 24 GB in use, leaving 8 GB free out of the shared 32 GB. The resource figures represent their assumed host memory footprint, including their overhead; the bar does not reserve all 32 GB for agents.

These are rounded illustrative GB figures, not measurements, Subyard defaults, or a guarantee of five simultaneous peak workloads. Overcommit does not create physical memory. Heavy work must be admitted against available capacity and headroom; requests may need to wait or be refused. Memory pressure, CPU, I/O, and virtualization overhead also affect usable concurrency.

This slide describes the desired operating model. Subyard's lease broker is one implementation example for the resource lifecycle, with its own configured pool limits.

Sources: Docker resource constraints: memory limits and host memory pressure; Docker isolation and shared host resources. Allocation sizes and the workload mix are presentation assumptions.

Slide 04 ↗

Different work. Different spaces.

The environment needs separate workspaces for different kinds of work and trust. Each workspace gives agents room to work within its own tools, access grants, and resource limits, while retaining its projects and useful session context. The three aligned rows make those choices explicit for every workspace.

The cards illustrate private development, client work, and a personal assistant. Tools might be Codex and development toolchains, a client's SDKs, or Hermes and assistant tools. Access might cover personal repositories and development keys, a single client's repositories and QA credentials, or selected files and a calendar. These are example configurations, not built-in product modes or a claim that Subyard ships each integration.

Resources are scoped policies on shared compute: CPU and RAM limits plus permission to request heavy resources when needed. A development or client workspace might lease a staging VM; an assistant can use a smaller ordinary budget and request heavier work separately. These limits do not reserve a fixed slice of physical RAM. Actual allocations still share the host capacity shown on slide 3.

Reuse common working rules and setup across spaces while keeping credentials and grants scoped to the work. Subyard is one implementation: it calls the workspace a yard and uses an Incus container or VM. Agents inside one yard share its trust and granted credentials. Separate project folders alone do not establish separate trust boundaries; mounts, network access, SSH grants, and credentials must also be controlled.

Sources: Product overview; Security boundary.

Sources: Yard trust boundary; Multiple yards and workflow model; Per-context credential delivery.

Slide 05 ↗

Choose capabilities per yard

The requirement is independent selection for each workspace while retaining shared working rules. Use real examples: Codex for the agent, Orca or Paseo for an interface, Codex Desktop as another client, an optional analytics service, and GitHub broker access. These choices can be combined; they are not mutually exclusive product editions.

The matrix is an illustrative configuration, not a report of an operator's yards. Dev uses Codex with Orca and OpenLIT. OpenClaw uses Codex with Paseo. A personal yard is connected to Codex Desktop. GitHub broker access is enabled for both dev and OpenClaw and left off for the personal yard. The same capability can be selected in multiple yards without forcing it into every yard.

In the current Subyard implementation, Codex and Paseo are agent integrations; Paseo requires Codex, and both example selections respect that dependency. Orca and OpenLIT are profiles. Codex Desktop connects through a selected yard's project export on a GNU/Linux desktop; it is a client connection rather than a guest profile switch. The GitHub profile controls per-yard wiring to the host-side broker. The ON cells illustrate selection; connection setup and authorization still determine readiness.

AI Observer is a real former analytics profile, but it is retired in the current Subyard implementation. It appears as an earlier replaceable option, not an available ON switch. OpenLIT is the current analytics example. Selecting or retiring one does not automatically select another.

Slide 06 ↗

Heavy resources, only while in use

The environment needs on-demand capacity for expensive checks. Sessions should be able to acquire a staging VM or Android emulator environment when needed, save the useful results, and release the allocation. Each resource needs an explicit lifecycle and a clear distinction between retained work context and temporary guest state.

Subyard's test-VM broker illustrates the pattern: a standard lease provides one or two VMs, an Android test lease provides a larger VM, and the Android profile prepares the emulator tooling. Fresh disks are created for each lease and deleted at release. Shared base images and reusable caches have their own retention rules. Other profile-owned services can legitimately have different lifetimes.

Sources: Disposable test VM pool and Android test leases; Android resources; Profile-owned resource lifecycles.

Slide 07 ↗

Every allocation has an owner

The environment needs accountable allocations: an owner, a resource, a lifetime, and a verified cleanup state. A broker should enforce capacity before acquisition, track heartbeats, and reclaim allocations that have been released or abandoned. A slot must not be handed to new work while its previous use is still active or cleanup is uncertain.

Subyard's broker is an example implementation. It fences access, stops and deletes disposable guests, and quarantines a slot when ownership verification or cleanup fails. Expiry invalidates lease rights; physical cleanup follows on a reaper pass. Do not promise instantaneous destruction at the deadline. The requirement is safe reclamation and reuse, including the failure path.

Sources: Lifecycle, fencing, reaper, and quarantine; Resource lease contract.

Slide 08 ↗

Reuse caches. Bound disk growth.

The environment needs both efficient cache reuse and a policy for reclaiming disk. Compatible project copies should reuse packages, toolchains, and intermediates. Outputs and evidence need clear owners; cleanup must account for active work before deleting data. Rust makes the cost of duplication particularly visible.

Subyard already illustrates scoped reuse with shared Go caches and Cargo intermediate groups keyed by compiler identity, while final outputs remain owned by their runs. Cargo handles concurrent build locking. Different flags or checkout remaps can still require rebuilds. Writable caches are shared state and should respect trust boundaries; writable Android Gradle caches are not shared indiscriminately across containers.

General reclamation, compiled-cache size limits, and automatic eviction remain work in progress in the Subyard example. They remain requirements for the environment even where an implementation does not yet satisfy them. Existing Cargo package-cache GC is separate.

Sources: Current shared Cargo workflow and lack of new compiled-cache eviction; Cache trust and locking; Android cache boundaries; disk cleanup roadmap goals.

Slide 09 ↗

Credentials across trusted hosts

The environment needs authorized staging credentials where work runs, without repeated manual copying or broad access grants. Trust enrollment, encrypted transport/storage, scoped delivery, synchronization, and rotation or conflict handling all need deliberate policies. Multiple worker hosts should share only what the workflow authorizes.

The diagram uses Subyard's host-side encrypted ledger as one implementation. Explicitly trusted peers exchange signed SOPS/age records; private host identities stay local, and only authorized consumer files materialize into a yard. Setup prepares the ledger and sync timer. Active peers initiate periodic sync; the cited implementation runs at least every six hours with boot catch-up and jitter.

Subyard limits this to selected static staging/QA records and excludes coding-agent OAuth/session stores. Different concurrent values require resolution. Removing a peer does not erase previously received secrets, so upstream rotation may be needed. These details illustrate the broader requirement for scoped credential lifecycle management.

Source: Host-side encrypted credential ledger, trust, materialization, and synchronization.

Slide 10 ↗

Compute across hosts. Skills for agents.

Two requirements extend the environment model: use the compute available across hosts, and make the environment's capabilities discoverable to the agents working in it.

Efficient use of compute — in planning. The proposed direction is for workers to borrow heavy resources from other Subyards, so a worker's current host does not bound all the compute it can use. The diagram illustrates a worker on host A requesting a staging VM on host B or Android emulator capacity on host C. These are examples of the intended model, not a shipped cross-host scheduler or automatic resource-placement feature. The design should retain capacity admission, scoped authorization, leases, and cleanup across the participating hosts.

Subyard already documents management of local and remote owner hosts, and its test-VM broker provides shared disposable resources. Those existing pieces do not establish that workers can currently lease resources from other independent Subyard hosts. Cross-host borrowing is the presentation's planning direction.

Agents know their environment. Expose Subyard capabilities through discoverable skills so agents can learn what is available, read the instructions, and use the supported interface. This describes awareness of the working environment and its available tools. Skill discovery does not itself grant access or provision a resource.

The shipped example is subyard-github: the selected GitHub profile installs a skill explaining temporary GitHub App authorization. Provisioning exposes it in the supported skill directories for Claude, Codex, OpenCode, pi, and Hermes. This is a concrete instance of the agent interface pattern; the cited implementation does not expose every Subyard function as a skill.

Sources at revision 8a2e38e147153ceab6019899078f5ae3acc2a188: Shipped subyard-github skill; Installation and agent discovery links; GitHub profile behavior; Existing remote-host workflows; Existing shared test-VM pool. Cross-host borrowing is a proposed direction for this presentation.

Slide 11 ↗

What the environment must provide

Close on the requirements, independent of the product: controlled access through isolation and scoped credentials; reusable setup through shared rules, optional profiles, and compatible caches; and bounded resource use through budgets, leases, and disk cleanup policies.

Subyard is one concrete implementation of these ideas. The examples show both existing mechanisms and unfinished work. The audience should leave with criteria for choosing or building an agent environment; other implementations can be evaluated against the same criteria. No benchmarked speedup or cost saving is asserted.
