Slide 02 ↗

Give agents a yard

Subyard puts projects, agents, tools, sessions, and optional service environments inside an isolated yard. The host can be a laptop, server, or VPS. Choose an Incus container or VM and set a CPU/memory budget. The yard gives the agent a place to work without automatically exposing the whole owner machine.

Isolation depends on the grants you make: mounts, SSH access, and credentials can expand the reachable scope. A VM is a stronger boundary, not a promise that every possible configuration is safe.

Sources: Product overview; Security boundary.

Slide 03 ↗

Container or VM?

The container shares the host’s Linux kernel while keeping a separate userspace. That gives low overhead and quick startup. A VM gets its own guest kernel and a hardware virtualization boundary, at a higher resource cost. Use it when the test or the trust boundary needs that separation.

The “Linux only” statement is scoped to Incus system containers. It is not a claim that every container technology on every platform is Linux-only. Incus VMs can support other operating systems in principle, but Subyard currently requires a Linux host and documents Debian/Ubuntu yard images. Native macOS/Windows Subyard host support is not claimed; those machines can run a Linux VM.

Sources: Incus: containers and VMs; Subyard environment model; Supported host platform.

Slide 04 ↗

A separate yard for each trust context

Organize around access: one yard for private development, separate yards for client work, another for a personal assistant. These are illustrative arrangements. Hermes is an illustrative workload, not a claimed built-in profile or tested integration at the cited revision. An assistant still needs the appropriate installation and explicit grants.

Within one yard, agents share a trust context and the credentials granted there. Merely putting two clients in separate project directories does not create separate yard isolation. Reuse configuration where helpful while keeping sensitive access scoped to the appropriate yard.

Sources: Yard trust boundary; Multiple yards and workflow model; Per-context credential delivery.

Slide 05 ↗

Shared rules. Optional profiles.

Shared instruction files establish consistent working habits. Profiles supply reusable toolchains, dependencies, and resources. Their selection is configurable per yard, so Android, test VM, or telemetry capabilities can be selected where needed. The switches are a conceptual diagram, not a live settings interface.

Agent integrations and environment profiles are separate configuration choices. Enable/disable runtime behavior is profile-specific: deselecting a capability does not imply deleting its data or credentials. The dedicated profile command applies to profiles with the appropriate owner service contract; broader selection is managed through configuration. Agent instructions are behavioral guidance, not an isolation boundary.

Sources: Configuration, agent rules, selections, and Git sources; Profiles and resources; Profile CLI scope; Rules versus security.

Slide 06 ↗

Heavy resources, only while in use

Several sessions do not each need a permanently running test stack. When a task needs a real machine, acquire a broker-managed lease. Boot a fresh guest, run the workload, collect useful evidence back into the workspace, then release it. The broker fences access and deletes the disposable guest disks.

The standard lease supports one or two standard VMs. Android testing uses a larger VM and the Android profile provides the SDK/emulator setup; the generic base does not automatically contain it. The pool is shared capacity, while each allocation is exclusive. Base images and reusable cache data survive lease cleanup. Other profile-owned staging services can have different retention rules.

Sources: Disposable test VM pool and Android test leases; Android resources; Profile-owned resource lifecycles.

Slide 07 ↗

About four sessions, with staging

The intended message is economical use of a modest host. The diagram budgets 32 GiB: four agent workloads at an assumed 2 GiB each, four one-VM staging allocations at 4 GiB each, and 8 GiB for the host, services, VM overhead, and headroom. The sum is 8 + 16 + 8 = 32 GiB.

This is a planning illustration supplied for the talk, not measured throughput, a minimum requirement, or a guarantee of four concurrent workloads. “32 GB class” is approximate; the arithmetic uses GiB. No current hardware price is claimed.

The documented default pool has two slots. Four simultaneous staging allocations require a suitably configured pool and enough underlying capacity. Each illustrated slot leases one standard VM, not a two-VM pair. Android leases use an 8 GiB VM, so they consume more of this budget. Builds, browser processes, CPU saturation, disk I/O, host reservation, and nested virtualization can change the result. Releasing stages between checks is what makes a shared pool practical.

Sources: illustrative capacity assumptions; Pool defaults, standard 4 GiB VM contract, and Android 8 GiB VM contract.

Slide 08 ↗

The broker owns the lease

The broker records who owns the allocation and for how long, refuses acquisition beyond capacity, and follows a cleanup protocol. When work completes or the heartbeat expires, access is fenced and the disposable machines are stopped and deleted. If ownership verification or cleanup fails, the slot is quarantined instead of being handed to another task.

Lease expiry and physical resource destruction are distinct. Expiry invalidates rights immediately; the broker starts cleanup on its next reaper pass. Do not promise zero residual resources at the precise deadline. The important guarantee is bounded admission and no reuse until the resource has reached a safe state.

Sources: Lifecycle, fencing, reaper, and quarantine; Resource lease contract.

Slide 09 ↗

Reuse caches. Bound disk growth.

Multiple checkouts should reuse compatible packages, toolchains, and build intermediates instead of independently duplicating them. The current development workflow already shares Go caches and groups Cargo build intermediates by compiler identity, while each run owns its final output directory and evidence. Cargo handles concurrent build locking.

Reuse is scoped by profile, compatibility, and trust. Different compiler flags or checkout remaps can cause rebuilds. A writable cache is shared mutable state, so it is not a security boundary; Android’s writable Gradle cache, for example, is not shared indiscriminately across container boundaries.

Broader disk reclamation, compiled-cache size limits, and automatic eviction are work in progress. Cargo’s existing package-cache GC is separate. The three cleanup rules on the slide are roadmap goals, not implemented promises.

Ordinary completed-run cleanup targets its own outputs. A broad cache wipe can remove shared intermediates still useful to other work. The long-term policy must account for ownership and active use before reclaiming disk.

Sources: Current shared Cargo workflow and lack of new compiled-cache eviction; Cache trust and locking; Android cache boundaries; disk cleanup roadmap goals.

Slide 10 ↗

Staging credentials across trusted hosts

Basic staging and QA secrets should not require repeated manual setup on every worker host. After explicit peer trust, the hosts exchange signed, encrypted ledger records. Selected static staging/QA records are imported into the ledger. Each host keeps its own private identity and materializes only the files authorized for a particular yard or consumer. The entire host credential store is never mounted into a yard.

Normal initialization prepares the ledger tools and timer. Active trusted peers initiate periodic synchronization; the documented timer runs at least every six hours, with boot catch-up and jitter. Manual immediate synchronization is also available. The diagram shows example trusted peer routes, not a cloud coordinator or automatic trust of every discovered machine.

Only selected static staging/QA records are in scope. Agent OAuth/session stores are excluded. Independent revisions can merge automatically; conflicting different values require resolution. Revoking trust cannot erase previously received credentials, so upstream rotation may still be necessary.

Source: Host-side encrypted credential ledger, trust, materialization, and synchronization.

Slide 11 ↗

The efficient working loop

Walk through a single task: choose the yard with the correct trust context, select the required profiles, acquire a test environment when verification needs it, and release the allocation after saving the result. Projects and session context remain useful between tasks. Leased test machines are disposable.

The efficiency comes from separating the lifetime of work context from the lifetime of expensive test capacity. Compatible caches improve reuse; the broker prevents an abandoned session from silently owning capacity forever. The general disk cleanup roadmap adds another layer as it matures.

Synthesis of slides 2–10 and the documented workflows.

Slide 12 ↗

More useful work from the same host

Close on the three mechanisms: bound agent access, reuse configuration and compatible caches, and release expensive resources. Subyard brings these into a repeatable workflow on compute you already control. The claim is a design goal and practical operating model, not a benchmarked speedup or cost reduction.
